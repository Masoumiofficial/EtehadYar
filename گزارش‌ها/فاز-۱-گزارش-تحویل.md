## ۲. مهم‌ترین تصمیم معماری: جداسازی *ساختاری* به‌جای *انضباطی*

رایج‌ترین راه شکست یک پلتفرم چندکاربره این است: توسعه‌دهنده در ۹۹ کوئری `AND user_id = x` را می‌نویسد و در کوئری صدم فراموش می‌کند — و دادهٔ کاربر A به کاربر B نشت می‌کند.

راه‌حل من: **هیچ‌کس نمی‌تواند کوئری بدون فیلتر کاربر بنویسد.** کلاس پایهٔ `Tenant_Repository` خودش عبارت `WHERE` را می‌سازد؛ زیرکلاس‌ها فقط اعلام می‌کنند کدام جدول را مدیریت می‌کنند:

```php
class Jobs_Repository extends Tenant_Repository {
    protected function table_key() { return 'jobs'; }
}
```

همهٔ متدها (`list_for`, `find`, `delete`, `count`, `insert`) مالکیت را اجباری می‌کنند. این یک قرارداد تیمی نیست — یک محدودیت ساختاری است.

**نکتهٔ ظریف:** در `find()` شرط مالکیت داخل خود `WHERE` است، نه بررسی بعد از واکشی. یعنی رکورد کاربر دیگر حتی یک لحظه هم در حافظه بارگذاری نمی‌شود.

## ۴. مهاجرت: رفع باگ H3 گزارش قبلی

در افزونهٔ قدیمی بلوک‌های مهاجرت به ترتیب **نزولی** نوشته شده بودند (`6119` قبل از `6113`) و هرکدام `eaiw_db_version` را می‌نوشت. نتیجه: روی سایت قدیمی فقط اولین بلوک اجرا می‌شد و بقیه هرگز.

پیاده‌سازی جدید:
- هر مهاجرت یک عدد نسخه دارد و همیشه **صعودی** اجرا می‌شود
- نسخه‌های اجراشده به‌صورت **آرایه** ذخیره می‌شوند، نه یک عدد
- قفل ۵ دقیقه‌ای جلوی اجرای همزمان را می‌گیرد
- اجرای دوباره no-op است (تست‌شده)

سه مهاجرت فاز ۱:

| نسخه | کار |
|---|---|
| 100 | ساخت جدول‌های `etehadyar_tenants` و `etehadyar_audit` |
| 110 | افزودن `user_id` + ایندکس به ۵ جدول قدیمی |
| 120 | نسبت‌دادن رکوردهای قبلی به مدیر سایت |

> `eaiw_vectors` عمداً روی `user_id = 0` می‌ماند: دانش سایت محتوای مشترک پلتفرم است، نه مالکیت خصوصی یک کاربر.

## ۵. پل سازگاری با افزونهٔ قدیمی

افزونهٔ AI را **فورک نکردم** — چون آن‌وقت رفع‌باگ‌های آینده‌اش غیرقابل ادغام می‌شد. به‌جای آن:

**الف) ثبت خودکار مالکیت.** فیلتر `query` رکوردهای `INSERT` افزونهٔ قدیمی را می‌گیرد و `user_id` را تزریق می‌کند. تطبیق عمداً بسیار محدود است: فقط `INSERT`، فقط جدول‌های شناخته‌شده، فقط وقتی ستون واقعاً غایب است. `SELECT` و جدول‌های دیگر دست‌نخورده می‌مانند (تست‌شده).

**ب) مسدودسازی عملیات مدیریتی.** ۱۵ اکشن AJAX قدیمی (تنظیمات، کرون، گزارش‌ها) پیش از رسیدن به هندلر قدیمی برای کاربر عادی بسته می‌شوند — حتی اگر بررسی بالادستی روزی خراب شود.

**ج) اجرا به‌نیابت.** `Legacy_Bridge::run_as($tenant_id, $callback)` برای Worker پس‌زمینه که کاربر لاگین‌شده ندارد.

## ۶. REST API

مسیر `etehadyar/v1` — **هیچ endpoint عمومی ندارد**. (افزونهٔ قدیمی مسیرهایی با `permission_callback => __return_true` داشت که هر مهمانی می‌توانست بکوبد.)

| مسیر | توضیح |
|---|---|
| `GET /me` | پروفایل، پلن، دسترسی‌ها |
| `GET /jobs` | کارهای کاربر + خلاصه |
| `GET /jobs/{id}` | یک کار — دسترسی متقابل ۴۰۴ می‌دهد |
| `GET /usage` | مصرف + سری روزانه |

**دو نکتهٔ امنیتی:**
- ستون `payload` هرگز برنمی‌گردد (می‌تواند prompt خام داشته باشد)
- دسترسی به کار کاربر دیگر **۴۰۴** می‌دهد نه ۴۰۳ — تا حتی وجود آن رکورد هم فاش نشود

## ۱۱. قدم بعدی — فاز ۲

ثبت‌نام و ورود با موبایل:
- جدول `etehadyar_otp` با کد **هش‌شده**، انقضای ۱۲۰ ثانیه

- اتصال به `Tenant::ensure()` — کاربر تأییدشده خودکار عضو پلتفرم می‌شود

برای شروع فاز ۲ فقط باید بدانم **کدام سرویس پیامک** را استفاده می‌کنید.
