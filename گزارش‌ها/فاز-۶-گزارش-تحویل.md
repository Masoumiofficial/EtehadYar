## ۱. حلقه‌ای که بسته شد

تا پایان فاز ۵ مشتری می‌توانست ثبت‌نام کند، شارژ کند، موجودی و تعرفه ببیند — اما **جایی برای خرج کردن نداشت**. فرم‌های تولید محتوا فقط در پیشخوان مدیر بودند و مشتری به پیشخوان راه ندارد.

کد کوتاه `[etehadyar_studio]` همان سطح گمشده است: سه ابزار (محتوا، تصویر، صدا) با زبانهٔ جداگانه، برآورد زندهٔ هزینه، و نمایش نتیجه در همان صفحه.

**تصمیم معماری مهم:** استودیو منطق تولید را بازنویسی **نمی‌کند**. همان اکشن‌های `admin-ajax.php` قدیمی را صدا می‌زند، چون:

- منطق اتصال به سرویس‌دهنده‌ها آنجاست و دوباره‌نویسی‌اش یعنی دو نسخهٔ واگرا،
- `admin-ajax.php` هوک `admin_init` را اجرا می‌کند، و **دقیقاً همان‌جا** رهگیر بیلینگ فاز ۴ و پل قابلیت‌های فاز ۵ نصب‌اند.

نتیجه: هر درخواست فرانت‌اند خودبه‌خود متر می‌خورد، سهمیه‌اش بررسی می‌شود و در صورت شکست بازگشت وجه می‌گیرد — بدون یک خط کد تکراری. تست این هم‌ارزی را می‌سنجد:

```
✔ underfunded studio request never reaches the provider
✔ no provider call made
✔ payment required
✔ balance untouched
```

## ۲. نشتی مالی که پیدا شد

هنگام بررسی خروجی‌ها، این را در `Vision_Studio::generate()` دیدم:

```php
// بدون کلید → SVG باکیفیت + راهنما
$svg = self::make_svg_placeholder($prompt, $style);
$att_id = self::save_svg_to_media($svg, $prompt);
return [
    'mode' => 'placeholder',
    'url'  => wp_get_attachment_url($att_id),
    ...
];
```

این مقدار از مسیر `wp_send_json_success()` برمی‌گردد. یعنی وقتی **کلید API وارد نشده** یا **سرویس‌دهنده خطا داده**، افزونه یک مستطیل رنگیِ محلی می‌سازد و آن را «موفق» اعلام می‌کند.

از دید بیلینگ فاز ۴، این یک کار موفق بود و **مبلغ کامل کسر می‌شد**. مشتری بابت تصویر هوش مصنوعی پول می‌داد و یک SVG ساده می‌گرفت.

این سناریوی نادری نیست: روزی که اعتبار سرویس‌دهنده تمام شود یا کلید منقضی شود، **همهٔ** کاربران پول می‌دهند و مستطیل می‌گیرند.

**رفع:** لایهٔ بیلینگ حالا پاسخ‌های «موفقِ تقلبی» را می‌شناسد. اگر `mode` یکی از `placeholder`/`error_fallback`/`fallback`/`stub` باشد، یا پاسخ فیلد `error` داشته باشد، کار **شکست‌خورده** تلقی و کل مبلغ برگردانده می‌شود. فهرست حالت‌ها با فیلتر `etehadyar_degraded_result_modes` قابل توسعه است.

صحت تست را با غیرفعال کردن موقت این گارد سنجیدم — دقیقاً ۲۰٬۰۰۰ ریال بابت یک placeholder کسر شد:

```
✘ PLACEHOLDER IMAGE IS NOT CHARGED (expected 10000000, got 9980000)
✘ ERROR FALLBACK IS NOT CHARGED   (expected 10000000, got 9980000)
```

پس از رفع، هر دو سبز — و تصویر واقعی همچنان درست حساب می‌شود.

## ۳. مانع دوم: کاربر نمی‌توانست کار خودش را پیگیری کند

کارهای سنگین در صف قرار می‌گیرند و باید وضعیتشان poll شود. اندپوینت موجود:

```php
public function ajax_job_status(){
    check_ajax_referer('eaiw_nonce');
    if(!current_user_can('manage_options')) wp_send_json_error('دسترسی غیرمجاز',403);
    $job = EAIW_Job_Queue::status(absint($_POST['id'] ?? 0));
```

دو مشکل هم‌زمان:
1. `manage_options` می‌خواهد — مشتری هرگز نمی‌تواند کار خودش را ببیند.
2. `Job_Queue::status($id)` **فقط با شناسه** جست‌وجو می‌کند. اگر صرفاً سطح دسترسی را پایین می‌آوردیم، هر مشتری می‌توانست با حدس شناسه، نتیجهٔ کار مشتری دیگر را بخواند.

**راه‌حل:** اندپوینت جدید `GET /etehadyar/v1/studio/job/{id}`. شرط مالکیت **بخشی از خود کوئری** است (`WHERE id = %d AND user_id = %d`)، نه فیلتری روی نتیجه — کار متعلق به دیگری اصلاً «پیدا نمی‌شود». ضمناً فقط فیلدهای لازم برای UI برگردانده می‌شوند، نه پاسخ خام سرویس‌دهنده.

```
✔ owner can read their own job
✔ ANOTHER MEMBER'S JOB IS NOT READABLE
✔ reported as not found, leaking nothing
```

## ۴. هماهنگی قیمت نمایشی با قیمت واقعی

قیمتی که کاربر پیش از اجرا می‌بیند، از همان `Pricing` خوانده می‌شود که سرور با آن کسر می‌کند — نه از یک ثابت جداگانه. شمارشگر کلمات جاوااسکریپت هم عمداً آینهٔ `Estimator::word_count()` است (حذف نیم‌فاصله، شمارش با یونیکد).

```
✔ displayed price for "content" comes from Pricing
✔ price change is reflected immediately
✔ the UI carries the live price
```

اگر مدیر تعرفه را عوض کند، UI بلافاصله همان را نشان می‌دهد.

## ۵. کنترل دسترسی در خود رابط

| وضعیت کاربر | آنچه می‌بیند |
|---|---|
| مهمان | دعوت به ورود — **بدون nonce** |
| معلق | پیام غیرفعال بودن حساب — **بدون nonce** |
| بدون دسترسی به یک ابزار | همان زبانه غیرفعال و علامت‌گذاری‌شده |
| عضو فعال | رابط کامل |

نکتهٔ `nonce` عمدی است: رابط غیرفعال بدون توکن معتبر یعنی حتی دستکاری DOM هم درخواست قابل‌قبولی نمی‌سازد.

| ۶ — استودیو و ایزولاسیون کار | ۴۹ | ALL PASS |
| **مجموع** | **۵۴۰** | **سبز** |

> **یک باور غلط در تست خودم:** ابتدا فرض کرده بودم کاربر با نقش `subscriber` یک «غیرعضو» است. تست شکست خورد و بررسی نشان داد **این رفتار درست محصول است**: گزینهٔ auto-enrol به‌صورت پیش‌فرض روشن است و هر ثبت‌نام جدید نقش عضو می‌گیرد. تست اصلاح شد تا کاربری را بسنجد که دسترسی‌اش **سلب شده** — که سناریوی واقعی «غیرعضو» است.
>
> سه کمبود هارنس هم رفع شد: `insert_id` پس از `query()` مستقیم، کلاس `WP_REST_Response`، و توابع `disabled()`/`selected()`/`esc_js()`.
