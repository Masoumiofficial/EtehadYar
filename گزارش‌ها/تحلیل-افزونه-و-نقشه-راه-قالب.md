# تحلیل افزونه اتحادیار ۶.۱۳.۲ و نقشهٔ راه تبدیل آن به قالب پلتفرم وردپرسی

تاریخ تحلیل: ۱۴۰۴/۰۶/۲۶ — منبع: `etehadyar-v6.13.2.zip` از مخزن Masoumiofficial/etehadyar

## ۱. خلاصهٔ مدیریتی

افزونهٔ اتحادیار یک **دستیار هوش مصنوعی چندمنظوره برای وردپرس** است: ۷۰ فایل، حدود ۵٬۸۰۰ خط PHP، ۳۷ کلاس، ۲۲ زیرمنوی مدیریت، ۱۳ جدول دیتابیس، ۳۸ اکشن AJAX و ۶ مسیر REST.

**نتیجهٔ کلیدی تحلیل:** معماری افزونه خوب و ماژولار است، اما **در وضعیت فعلی روی سایت زنده کرش می‌کند** (دو باگ Fatal پیدا شد که هر دو را اصلاح کردم — بخش ۴). مهم‌تر از آن: افزونه **کاملاً تک‌کاربره و ادمین‌محور** است. هیچ مفهومی از «کاربر»، «اعتبار/شارژ»، «پلن»، «پرداخت» یا «ثبت‌نام با موبایل» در آن وجود ندارد. یعنی تبدیل آن به پلتفرم SaaS، **بازنویسی لایهٔ کاربر از صفر** است، نه صرفاً «انتقال کد به قالب».

| معیار | وضعیت |
|---|---|
| کیفیت معماری (لایه‌بندی، Autoload، صف کار) | خوب ✅ |
| امنیت لایهٔ ادمین (nonce + capability روی هر ۳۸ AJAX) | خوب ✅ |
| سلامت اجرا (syntax) | ۲ باگ Fatal — اصلاح شد ⚠️→✅ |
| آمادگی برای چندکاربره (multi-tenant) | صفر ❌ |
| سیستم اعتبار/شارژ/پرداخت | وجود ندارد ❌ |
| ثبت‌نام با موبایل / OTP | وجود ندارد ❌ |
| قابلیت ترجمه (i18n) | صفر — همهٔ متن‌ها هاردکد فارسی ❌ |

### ۲.۲ جداول دیتابیس (۱۳ عدد)

`eaiw_vectors` · `eaiw_agents` · `eaiw_jobs` · `eaiw_automations` · `eaiw_automation_runs` · `eaiw_chatsoul_logs` · `eaiw_chat_feedback` · `eaiw_activity_log` · `eaiw_usage` · `eaiw_support_requests` · `eaiw_support_history`

**نکتهٔ حیاتی:** در هیچ‌کدام از این جدول‌ها ستون `user_id` برای جداسازی داده بین کاربران وجود ندارد (به‌جز `activity_log` که فقط برای لاگ است). این یعنی معماری ذاتاً تک‌مستأجری است.

### ۲.۳ نقاط قوت واقعی

1. **`EAIW_Vault`** — رمزنگاری AES-256-GCM با کلید مشتق‌شده از `AUTH_KEY + SECURE_AUTH_SALT`. استاندارد و درست.
2. **`EAIW_Job_Queue`** — صف کار کامل با retry نمایی (۶۰s → ۳۰۰s → ۱۵۰۰s)، سقف همزمانی per-type، بازیابی کارهای معلق، و قفل Worker. این همان زیرساختی است که برای SaaS لازم دارید.
3. **`EAIW_AI_Client`** — fallback هوشمند بین ۴ ارائه‌دهنده. اگر اعتبار OpenAI تمام شود خودکار سراغ GapGPT می‌رود. برای بازار ایران طراحی شده.
4. **امنیت AJAX** — هر ۳۸ هندلر AJAX هم `check_ajax_referer` دارند هم `current_user_can`. این نقطه‌قوت جدی است.
5. **`EAIW_Usage`** — ثبت مصرف توکن با تخمین هزینه. **این ستون فقرات سیستم شارژ آیندهٔ شماست.**

### 🟡 کیفیت کد

- **i18n صفر** — هیچ `__()` یا `_e()` در کل کد نیست. پوشهٔ `languages/` هم وجود ندارد در حالی که `load_plugin_textdomain` صدا زده می‌شود. برای محصول تجاری قابل قبول نیست.
- **`EAIW_Plugin` خدای کلاس** — ۷۱۴ خط، ۳۸ هندلر AJAX، منطق migration، و enqueue همه در یک کلاس.
- کد فشرده‌شده در یک خط (`class-usage.php` کل کلاس در ۶ خط) — نگهداری را سخت می‌کند.
- `EAIW_Woo_GodMode` محتوای کاملاً هاردکد تولید می‌کند («۱۸ ماه گارانتی اتحاد») — ادعای دروغ برای هر فروشگاهی که نصبش کند.
- `similar_text()` در ChatSoul روی UTF-8 بایت‌محور عمل می‌کند → تطبیق FAQ غیرقابل‌اتکا.

## ۵. نقشهٔ راه: از افزونه به قالب پلتفرم

### ۵.۱ تصمیم معماری — مهم‌ترین بخش این گزارش

شما خواسته‌اید «قالبی بسازیم که روی وردپرس خام نصب شود و همهٔ امکانات در قالب باشد». **توصیهٔ فنی من: این کار را به‌صورت «همه‌چیز داخل قالب» انجام ندهید.**

دلایل:

1. اگر کاربر قالب را عوض کند، **کل پلتفرم، اعتبار کاربران و داده‌ها از کار می‌افتد**. منطق تجاری هرگز نباید در قالب باشد — این قانون طلایی وردپرس است.
2. قالب‌ها در دایرکتوری وردپرس و بازارها با قوانین سخت‌گیرانه‌تری بررسی می‌شوند؛ «functionality in theme» دلیل رد شدن است.
3. به‌روزرسانی قالب، فایل‌های شما را overwrite می‌کند.

**معماری پیشنهادی — «قالب + افزونهٔ همراه» (Theme + Companion Plugin):**

```
┌──────────────────────────────────────────────────────┐
│  قالب (etehadyar-theme)                              │
│  فقط ظاهر: صفحهٔ فرود، پنل کاربری، فرم ورود،         │
│  قیمت‌گذاری، بلاگ، RTL، رنگ‌بندی، Customizer         │
└────────────────────┬─────────────────────────────────┘
                     │ فقط فراخوانی تابع/شورتکد
┌────────────────────┴─────────────────────────────────┐
│  افزونهٔ هسته (etehadyar-core) — اجباری              │
│  ├── موتور AI (از افزونهٔ فعلی)                       │
│  ├── حساب کاربری + OTP موبایل                        │
│  ├── کیف پول / اعتبار / اشتراک                        │
│  ├── درگاه پرداخت (زرین‌پال و…)                       │
│  ├── سهمیه‌بندی و محدودیت per-user                    │
│  └── REST API برای فرانت                             │
└──────────────────────────────────────────────────────┘
```

قالب با TGM-Plugin-Activation افزونهٔ هسته را اجباری نصب می‌کند. برای کاربر نهایی تجربه یکسان است («یک قالب نصب می‌کنم و همه‌چیز کار می‌کند») ولی معماری سالم می‌ماند.

> اگر روی «همه‌چیز در قالب» اصرار دارید، حداقل کل کد را در `inc/` قالب بگذارید و از `after_switch_theme` برای ساخت جداول استفاده کنید — ولی بدانید ریسک از دست رفتن داده هنگام تعویض قالب را پذیرفته‌اید.

### ۵.۲ چیزهایی که باید از صفر ساخته شوند

هیچ‌کدام از این‌ها در افزونهٔ فعلی وجود ندارد:

#### الف) ثبت‌نام و ورود با موبایل (OTP)

```php
// جدول جدید
wp_eaiw_otp: id, phone(varchar 15, index), code_hash(varchar 64),
             attempts(tinyint), expires_at(datetime), ip(varchar 45), created_at

// user meta
_eaiw_phone           // 09xxxxxxxxx نرمال‌شده
_eaiw_phone_verified  // 0/1
```

**نکات پیاده‌سازی:**
- نرمال‌سازی شماره: `+98`, `0098`, `98`, `09` → یک فرمت واحد `9xxxxxxxxx`
- کد ۵ یا ۶ رقمی، **هش‌شده** ذخیره شود (نه plain)، اعتبار ۱۲۰ ثانیه
- Rate limit سه‌لایه: حداکثر ۱ درخواست در ۶۰ ثانیه برای هر شماره، ۵ در ساعت برای هر IP، قفل شماره بعد از ۵ تلاش ناموفق
- `username` را از شمارهٔ موبایل بسازید، ایمیل ساختگی `9xxxxxxxxx@phone.local` تا وردپرس راضی شود
- پنل انتخاب سرویس پیامک: کاوه‌نگار، ملی‌پیامک، فراز‌اس‌ام‌اس، SMS.ir — با اینترفیس مشترک `EAIW_SMS_Gateway`
- reCAPTCHA یا حداقل honeypot روی فرم ارسال کد

#### ب) کیف پول و سیستم اعتبار

```php
wp_eaiw_wallet:       user_id(PK), balance(decimal 12,2), updated_at
wp_eaiw_transactions: id, user_id, type(enum: charge|consume|refund|bonus|admin),
                      amount, balance_after, ref_id, description, meta, created_at
wp_eaiw_plans:        id, title, price, credits, duration_days, features(json), is_active
wp_eaiw_subscriptions: id, user_id, plan_id, starts_at, expires_at, status
```

**قانون طلایی:** اعتبار باید **قبل از** فراخوانی API رزرو شود و بعد از نتیجه تسویه گردد:

```
۱. تخمین هزینه → ۲. بررسی موجودی → ۳. رزرو (کسر موقت)
→ ۴. اجرای کار → ۵. محاسبهٔ مصرف واقعی از EAIW_Usage
→ ۶. تسویه (بازگشت مابه‌التفاوت) یا ۷. بازگشت کامل در صورت شکست
```

جدول `eaiw_usage` موجود دقیقاً برای همین ساخته شده — فقط باید `user_id` به آن اضافه شود.

#### ج) درگاه پرداخت

اینترفیس `EAIW_Payment_Gateway` با پیاده‌سازی زرین‌پال (پیش‌فرض)، آی‌دی‌پی، نکست‌پی، زیبال. جریان: درخواست → ریدایرکت → callback → **تأیید سمت سرور (verify)** → شارژ کیف پول. هرگز به پارامترهای بازگشتی مرورگر اعتماد نکنید.

#### د) پنل کاربری فرانت‌اند

صفحات: داشبورد · تولید محتوا · تصویرساز · چت · تاریخچه · کیف پول · خرید اعتبار · تنظیمات حساب

**نکتهٔ امنیتی حیاتی:** هر ۳۸ اکشن AJAX فعلی `current_user_can('manage_options')` یا `edit_posts` چک می‌کنند. برای کاربر عادی باید **یک لایهٔ کاملاً جدید** با کپابیلیتی `eaiw_use_platform` نوشته شود — هرگز کپابیلیتی ادمین را به مشتری ندهید.

#### ه) جداسازی داده بین کاربران (Multi-tenancy)

به این جدول‌ها باید `user_id` اضافه شود و **هر کوئری فیلتر گردد**:
`eaiw_jobs` · `eaiw_usage` · `eaiw_chatsoul_logs` · `eaiw_support_requests` · `eaiw_vectors`

این پرخطرترین بخش کار است: یک کوئری فراموش‌شده = نشت محتوای کاربر A به کاربر B.

**نکات فنی قالب:**
- `functions.php` باید با `if (!function_exists('eaiw_core_active'))` شروع شود تا نبود افزونه باعث کرش نشود
- RTL کامل: `rtl.css` + `is_rtl()`
- فونت وزیرمتن **لوکال** (نه CDN — به‌خاطر تحریم و سرعت در ایران)
- سازگاری با تاریخ شمسی برای نمایش تراکنش‌ها
- Block Editor ready + Full Site Editing (اختیاری ولی امتیاز مثبت)

## ۶. توصیهٔ نهایی

| اولویت | اقدام |
|---|---|
| ۱ | **فوری:** نصب بستهٔ hotfix — افزونهٔ فعلی روی محصول ووکامرس و پشتیبانی صوتی کرش می‌کند |
| ۲ | تصمیم‌گیری دربارهٔ معماری (پیشنهاد من: قالب + افزونهٔ همراه) |
| ۳ | رفع H1 (embedding واقعی) و H2 (شمارش کلمهٔ فارسی) — این دو، هستهٔ «هوشمندی» را از حالت نمایشی خارج می‌کنند |
| ۴ | حذف یا بازنویسی کامل `Woo_GodMode` و `Oracle` — داده‌های ساختگی در محصول تجاری ریسک حقوقی دارند |
| ۵ | شروع فاز ۱ (multi-tenancy) — بقیهٔ فازها بدون آن معنا ندارند |

**برآورد واقع‌بینانه:** حجم کدی که باید نوشته شود (لایهٔ کاربر، پرداخت، OTP، سهمیه، قالب) تقریباً **به اندازهٔ کل افزونهٔ فعلی** است. این یک محصول جدید است که از موتور AI افزونهٔ موجود استفاده می‌کند — نه یک مهاجرت ساده.
