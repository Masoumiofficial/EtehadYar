# فاز ۱۰ — آزمون یکپارچه روی وردپرس واقعی و MySQL

تا پیش از این فاز، همهٔ ۷۵۱ آزمون روی یک **شبیه‌ساز وردپرس با SQLite** اجرا می‌شد. این فاز
بسته‌ها را روی یک نصب واقعی وردپرس با MySQL واقعی آزمود. نتیجه: **سه باگ که SQLite هرگز
نمی‌توانست نشان دهد** پیدا و رفع شد.

---

| مؤلفه | نسخه |

| وردپرس | **7.1** (نصب تازه) |
| پایگاه‌داده | MariaDB **11.8.6** (پروتکل MySQL) |

نصب دقیقاً از همان سه zipیی انجام شد که به شما تحویل داده می‌شود — نه از سورس.

## باگ ۱ (بحرانی) — ستون گم‌شده در مهاجرت `activity_log`

**چه دیدیم:** بلافاصله پس از فعال‌سازی افزونهٔ قدیمی، `debug.log` پر شد از:

```
WordPress database error Invalid default value for 'id' for query
ALTER TABLE wp_eaiw_activity_log ALTER COLUMN `id` SET DEFAULT 'info'
```

**چرا:** جدول `eaiw_activity_log` در دو جا تعریف شده بود — یک‌بار در `class-activator.php`
(با ستون `level`) و یک‌بار در مهاجرت `dbv < 689` در `class-plugin.php` (**بدون** `level`).
`dbDelta` این دو را مقایسه می‌کرد، فهرست ستون‌ها یک واحد جابه‌جا می‌شد، و مقدار پیش‌فرض
`'info'` که متعلق به `level` بود به کلید اصلی `id` نسبت داده می‌شد.

**چرا خطرناک بود:** این کد روی هوک `init` است، یعنی خطا **در هر بار بارگذاری صفحه** تکرار
می‌شد و لاگ سایت مشتری را پر می‌کرد.

**رفع:** ستون `level varchar(12) NOT NULL DEFAULT 'info'` به تعریف مهاجرت اضافه شد.

## باگ ۲ (بحرانی) — `dbDelta` تمام ایندکس‌ها را بی‌صدا دور می‌انداخت

این جدی‌ترین یافتهٔ فاز بود و فقط به این دلیل پیدا شد که به خطای اول قانع نشدم.

**چه دیدیم:** حتی پس از رفع باگ ۱، خطاهای دیگری ماند:

```
ALTER TABLE wp_eaiw_chat_feedback ADD  `` (``)
```

نام ایندکس و نام ستون **خالی** بودند.

**چرا:** `dbDelta` برای تشخیص ایندکس‌ها یک regex دارد که **وجود فاصله بین نام ایندکس و
پرانتز باز را الزامی می‌کند**. کد قدیمی همه‌جا `KEY session_id(session_id)` می‌نوشت —
بدون فاصله. من این را مستقیماً روی regex خود هستهٔ وردپرس آزمودم:

| نوشته‌شده در کد | نتیجهٔ regex وردپرس |
|---|---|
| `PRIMARY KEY(id)` | ✗ شکست |
| `KEY session_id(session_id)` | ✗ شکست |
| `UNIQUE KEY ticket_key(ticket_key)` | ✗ شکست |
| `PRIMARY KEY  (id)` | ✓ موفق |
| `KEY session_id (session_id)` | ✓ موفق |

**پیامد واقعی:** هر ایندکسی که `dbDelta` می‌ساخت دور انداخته می‌شد. روی جدول‌هایی مثل
`eaiw_jobs` و `eaiw_usage` که با رشد سایت بزرگ می‌شوند، این یعنی **پویش کامل جدول** در هر
کوئری — کندی تدریجی که هیچ‌وقت به‌عنوان «خطا» دیده نمی‌شد.

**رفع:** ۳۶ عبارت کلید در دو فایل اصلاح شد. پس از رفع، ایندکس‌ها واقعاً ساخته می‌شوند:

| جدول | تعداد ایندکس |
|---|---|
| `eaiw_activity_log` | ۵ |
| `eaiw_support_requests` | ۵ |
| `eaiw_chat_feedback` | ۴ |
| `eaiw_jobs` · `eaiw_usage` · `eaiw_vectors` · `eaiw_support_history` | ۳ |
| `eaiw_agents` · `eaiw_automations` · `eaiw_chatsoul_logs` | ۲ |

## باگ ۳ — تعریف جدول‌ها در یک خط

`dbDelta` بدنهٔ `CREATE TABLE` را **خط‌به‌خط** تجزیه می‌کند؛ هر ستون و هر کلید باید در خط
خودش باشد. چند مهاجرت، کل جدول را در یک خط فشرده نوشته بودند. ۱۵ تعریف جدول بازقالب‌بندی شد.

**نتیجهٔ نهایی هر سه رفع:** `debug.log` از **۲۲ خطا** به **صفر** رسید، و پس از ۵ بارگذاری
صفحهٔ دیگر هم صفر ماند (یعنی مهاجرت‌ها idempotent هستند و دوباره تلاش نمی‌کنند).

## آزمون‌های عملکردی روی MySQL واقعی

### مسیر پول — کامل
```
✅ کاربر با نقش etehadyar_member ساخته شد
✅ سطر tenant در MySQL ثبت شد
✅ کیف پول جدید از صفر شروع می‌شود
✅ شارژ ۵۰۰٬۰۰۰ ریالی            balance=500000
✅ کسر ۱۲۰٬۰۰۰ ریالی             balance=380000
✅ برداشت بیش از موجودی رد شد     code=etehadyar_wallet_insufficient
✅ موجودی پس از رد تغییر نکرد     balance=380000
✅ دفتر append-only دقیقاً ۲ سطر دارد
✅ هیچ موجودی منفی در کل جدول نیست
```

### آزمون همزمانی — چیزی که SQLite هرگز نمی‌توانست بسنجد
۱۰ درخواست کسر ۳۰٬۰۰۰ ریالی **به‌طور همزمان** روی موجودی ۱۰۰٬۰۰۰ ریال:

```
OK OK OK REJECT REJECT REJECT REJECT REJECT REJECT REJECT
✅ دقیقاً ۳ کسر موفق شد
✅ هرگز منفی نشد
✅ دفتر با موجودی می‌خواند (۱۰٬۰۰۰ + ۹۰٬۰۰۰ = ۱۰۰٬۰۰۰)
```

قفل اتمی `WHERE balance >= %d` زیر فشار واقعی درست کار می‌کند — این مهم‌ترین تضمین مالی
سامانه است و حالا روی موتور واقعی اثبات شده.

### چرخهٔ کامل OTP
```
✅ کد از طریق درگاه ارسال شد
✅ کد ۵ رقمی است
✅ در MySQL ذخیره شد
✅ فقط به‌صورت hash‌ی sha256 — متن خام هیچ‌جا نیست
✅ کد اشتباه رد شد
✅ کد درست تأیید شد
✅ کد دوبار قابل استفاده نیست (replay مسدود)
```
نکتهٔ خوب: وقتی درگاه پیامک پیکربندی نشده باشد، سامانه **صادقانه خطا می‌دهد** و کد جعلی
نمی‌سازد.

### کنترل دسترسی و جداسازی مشتریان
```
✅ بازدیدکنندهٔ ناشناس در /wallet فقط فرم ورود می‌بیند — هیچ عددی درز نمی‌کند
✅ کاربر پس از ورود موجودی خودش را می‌بیند (۷۷۷٬۷۷۷)
✅ REST بدون ورود: /wallet /me /usage /jobs → هر چهار 401
✅ دستکاری پارامتر برای خواندن کیف پول کاربر دیگر بی‌اثر بود:
   user_id=6 · id=6 · tenant_id=6 · user=6 → همگی فقط موجودی خودِ درخواست‌کننده
```

### صفحات و رندر
```

✅ هر چهار صفحه HTTP 200
✅ قالب در حالت RTL رندر می‌شود
```

## دو موردی که هشدار کاذب بودند

برای شفافیت، دو چیز که اول شبیه باگ به نظر رسیدند و نبودند:

1. **«هیچ جدولی ساخته نشده»** — `grep` من دنبال `wp_eaiw%` گشت، در حالی که جدول‌های هسته
   پیشوند `wp_etehadyar%` دارند. جدول‌ها از اول درست ساخته شده بودند.
2. **«موجودی به کاربر ناشناس درز کرد»** — الگوی `777` در صفحه پیدا شد، ولی بررسی دقیق نشان
   داد این کد رنگ CSS `color:#777` است، نه موجودی کیف پول.

در هر دو مورد، پیش از اعلام باگ، خروجی خام بررسی شد.
